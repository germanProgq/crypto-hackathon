The Platform: A Telegram‑Native, Multi‑Round Auction Engine with Crypto Balances (RU/EN)

In the same way Telegram evolved from “a messenger” into an ecosystem for communities, creators, and automation, this platform is designed as a Telegram-native marketplace engine where scarce digital goods are allocated through a multi‑round auction inspired by Telegram Gift Auctions. The product looks simple on the surface—users top up a balance, place bids, win limited slots or digital items, and withdraw crypto—but under the hood it is a high‑performance, financially correct, concurrency‑safe system built like real infrastructure. From day one, the platform ships bilingual (Russian and English) across the Telegram bot and the minimal web UI: every message, button, error, and notification is localized via an i18n layer with consistent keys, fallbacks, and locale detection. That matters because a marketplace is not just code—it’s trust, clarity, and a user experience that behaves identically in both languages, including money flows and edge-case messaging.

Product Mechanics: Multi‑Round Allocation, Not a Toy Auction

This is not a single-deadline “highest bid wins” demo. Each auction is configured as a sequence of rounds, and each round allocates only a portion of winners. Winners exit immediately with a “delivery record” (a slot, access, role, or other digital good), while non‑winners continue into the next round. This format models real scarcity distribution while keeping the competition alive across multiple checkpoints. To protect fairness, the platform implements anti‑sniping: if bids land in the last seconds of a round, the round extends by a controlled amount (with hard caps), ensuring a final‑second spam attack cannot decide the outcome. Ranking is deterministic, tie‑breakers are explicit, and every rule is captured in a spec: where the behavior is ambiguous, the system documents assumptions and makes them testable.

The Financial Core: Ledger‑First, Escrow‑Backed Bidding

A hackathon project becomes production‑ready the moment it treats money as a first‑class invariant. The platform uses a ledger-first architecture: every balance change is an append‑only entry (deposit confirmed, hold created, hold released, hold captured, withdrawal requested, withdrawal broadcasted, withdrawal confirmed). Instead of “updating a balance field and hoping it’s correct,” the balance is derived from ledger events and validated continuously. Bidding is escrowed: when a user increases a bid, the system reserves only the delta required, preventing both over‑locking and double‑spend. When a round ends, winners trigger a capture (funds become spent), while everyone else triggers a release (funds return to available balance). This design is resilient because it’s reversible, auditable, and idempotent—exactly what you want under race conditions, retries, and partial failures.

Crypto Rails: Automatic Deposits and Safe Withdrawals

The platform’s “wallet layer” is intentionally minimal and safe: automatic deposits credit internal balances only after required confirmations, and withdrawals follow a strict state machine (requested → authorized → broadcasted → confirmed/failed). The deposit pipeline is built around idempotency: the same transaction hash (or memo) cannot be credited twice, even if the watcher restarts, nodes return inconsistent results, or webhooks are delivered multiple times. For withdrawals, the system isolates key material and treats signing as a privileged operation—keys are never logged, never embedded in images, never exposed to the bot process, and never reachable from the public edge. The platform is compatible with multiple approaches: address-per-user (HD derivation), memo/tag attribution, or a controlled set of deposit addresses with deterministic mapping. In production hardening, signing moves behind KMS/HSM boundaries; in MVP, it is still separated into a “hot signer” service with aggressive network and IAM restrictions.

Tech Stack: Fast Path Performance on Node.js + TypeScript + MongoDB

The stack centers on Node.js + TypeScript for velocity without sacrificing correctness, MongoDB as the system of record, and Redis as the low-latency accelerator for ranking, locks, and rate limits. The service layout is modular: an Auction Engine (round lifecycle, ranking, anti-sniping), a Balance/Ledger service (holds, captures, releases), a Crypto Gateway (watchers + withdrawals), a Telegram Bot service (UI and notifications), and a small Web UI for demo and observability. MongoDB stores truth: auctions, bids, ledger entries, round results. Redis speeds the hot paths: per-auction sorted sets for top‑N ranking, distributed locks for round finalization, short TTL caches for “current state,” and token-bucket rate limiting to stop spam without harming legitimate bidders.

“Insane” Optimization: Designing for Speed Without Breaking Correctness

Winning systems don’t just scale—they stay correct while scaling. The most performance‑critical path is placing a bid under high concurrency. The optimized flow is: validate user + auction state, compute required delta, acquire a short lock (per auction-round), run a MongoDB transaction that writes the bid and ledger hold atomically, then update Redis ranking as a cache. Reads are structured so that the UI rarely touches MongoDB directly in real time: live auction pages read from Redis state snapshots (current round, remaining time, top bids), while Mongo remains the authoritative audit trail. Indexing is non‑negotiable: compound indexes on (auctionId, roundIndex, amount desc, createdAt asc) for ranking queries, and (userId, createdAt) for ledger history. Round closing is also optimized: instead of scanning every bid repeatedly, the engine pulls the top‑K efficiently (from Redis with verification against Mongo on close), writes a results document once, and performs batched ledger transitions. For speed under load, the platform uses coarse-grained caching (state snapshots) and fine-grained invalidation (on new top bid). The result is low tail latency: the system aims for sub‑100ms median bid acceptance under normal load, while still being safe under bursty “last seconds” bidding.

A key performance principle here is bounded work. Anti-sniping is implemented with strict caps to prevent infinite extensions. Ranking reads are limited to top‑N with pagination rather than unbounded lists. Notifications are queued, not performed inline. The engine never blocks on third‑party calls during bid placement. Every background action is moved to workers: sending Telegram messages, settlement transitions, deposit confirmations, withdrawal broadcasting. This separation keeps the critical bid endpoint fast, predictable, and measurable.

Concurrency Guarantees: Idempotency, Locks, and Deterministic State Machines

When thousands of bids arrive at the same time, concurrency bugs don’t show up as “errors”—they show up as money disappearing or winners duplicating. The platform prevents that by combining three mechanisms: idempotency keys for all money-moving commands, distributed locks for single-writer transitions (round close, auction finalize), and deterministic state machines for auction/round progression. Bid placement is safe even if a client retries: the idempotency token ensures the same logical bid update can’t reserve funds twice. Round finalization is safe even if a worker crashes halfway: re-running finalization either completes missing steps or no-ops due to state checks. Every step is designed to be reentrant.

Security: Threat Modeling, Hardening, and Auditability

Security is not a feature; it’s the platform’s foundation. The bot layer never holds sensitive secrets, and never executes privileged operations. Authentication is anchored on Telegram identity, with server-side session tokens for the web UI and strict separation between “public API” and “internal worker API.” All secrets are injected at runtime from a secret manager, rotated regularly, and blocked from logs by default. Rate limits exist at three levels: per IP, per Telegram user, and per auction (to stop bid floods). Every “money” operation emits an audit event to an immutable log, allowing full reconciliation: the system can prove that total deposits minus total withdrawals equals total user balances plus reserved holds, at any time. Data is encrypted in transit, strict CORS and CSRF protection is applied to web endpoints, and every external callback (watchers/webhooks) is verified and replay‑protected.

Withdrawal security gets “insane” by design: it uses cooldowns, minimum thresholds, address allowlists per user, anomaly detection (sudden large withdrawals, many small withdrawals, multiple destination addresses), and a tamper‑evident approval path. In production, the platform supports multi-sig or policy-based signing; even in MVP, it keeps signing isolated and observable, with strict resource controls and explicit failure handling.

Demonstrability: A System You Can Watch Under Fire

The platform includes a load suite (k6/Artillery or custom scripts) that simulates hundreds or thousands of concurrent bidders, especially in the last seconds of a round to stress anti‑sniping. The demo proves invariants: no negative balances, no duplicate winners, no lost holds, and consistent end-state reconciliation. Observability is built in: metrics for bid throughput, transaction duration, lock contention, round extension count, and settlement times. When judges watch it, they don’t just see a UI—they see a real engine behaving correctly under pressure.

This is the point of the platform: a Telegram-native auction product that feels simple, but is engineered like serious financial infrastructure—fast, deterministic, bilingual (RU/EN), and brutally correct even when the system is under attack or under load.
